# Sift v0.2 Hardening and Accuracy Design

Date: 2026-08-16
Status: Approved
Owner: KJyang-0114

## Purpose

Sift v0.2 will first establish a trustworthy security and testing foundation, then improve scanner accuracy. Breaking changes are allowed, but every change must be documented in `MIGRATION.md`. Each pull request must build and test independently, include risk and rollback notes, and wait for maintainer review before the next pull request begins.

## Product decisions

- Linux and macOS receive the complete feature set. Windows supports analysis but never executes generated code.
- Dynamic execution is disabled by default and requires `--enable-execution`.
- Generated code runs only through an approved container backend. Direct host execution is removed.
- LLM analysis is offline by default. It starts only after the user configures a provider/API key and acknowledges that selected source code will be sent to that provider.
- Accuracy is the primary Stage B goal. Only evidence-backed, high-confidence findings may block a pull request.
- Stage A produces `v0.2.0-alpha.1`; Stage B produces `v0.2.0`.

## Architecture

The CLI is a delivery layer. It parses user input, loads policy, invokes the application service, and renders errors. It must not read arbitrary target files, execute commands, or call an LLM directly.

The core is split into six boundaries:

1. **CLI** — commands, flags, user prompts, and exit codes.
2. **Policy and configuration** — offline mode, upload consent, provider configuration, execution permission, platform capability, resource limits, and output policy.
3. **Target resolver** — repository root discovery, canonical paths, Git diff targets, ignore rules, file type/size limits, and symlink containment.
4. **Analysis engine** — analyzer scheduling, concurrency, cancellation, timeout, result collection, normalization, and deduplication.
5. **Analyzers** — Semgrep, dependency verification, and optional LLM analysis. Analyzers return normalized findings and cannot reach external systems except through injected interfaces.
6. **Integrations** — command runner, registry client, LLM client, and generated-code executor. Tests replace all integrations with fakes.

Data flows in one direction:

```text
CLI
  -> policy and explicit consent
  -> target resolver
  -> analysis engine
  -> deterministic analyzers
  -> optional LLM analyzer
  -> finding normalization and deduplication
  -> terminal, JSON, SARIF, or LLM report
```

## Core contracts

### Finding v2

Every finding contains:

- stable `id` and `fingerprint`;
- analyzer `source` and rule identifier;
- normalized severity and category;
- confidence (`high`, `medium`, or `low`);
- primary location and optional related locations;
- concrete evidence, including a bounded snippet or dependency fact;
- remediation text and optional `help_uri`;
- suppression state and reason.

The fingerprint is derived from analyzer namespace, rule, canonical repository-relative path, and a stable location/message key. Secrets and absolute host paths never participate in serialized output.

### Analyzer

Analyzers accept a context, an immutable scan request, resolved targets, and injected dependencies. They return findings plus typed diagnostics. They do not render output, persist state, prompt users, or terminate the process.

### External integrations

`CommandRunner`, `RegistryClient`, `LLMClient`, and `Executor` are narrow interfaces. Implementations enforce timeout and output limits. Callers pass argument arrays, never shell command strings.

## Configuration and CLI

The v0.2 configuration groups policy explicitly:

```toml
[privacy]
offline = true
allow_source_upload = false
redact_secrets = true

[execution]
enabled = false
backend = "auto" # auto | docker | podman | none
network = false
timeout_seconds = 30
memory_mb = 256
cpus = 1
pids = 64

[analysis]
concurrency = 4
timeout_seconds = 120
minimum_confidence = "medium"

[llm]
provider = "offline"
model = ""

[output]
format = "terminal"
color = true
```

API keys remain environment-first. A local key may be stored only when the user explicitly requests it, and its file permissions must be restricted. Keys are never stored in scan history.

Cloud LLM activation requires both provider credentials and an acknowledgement recorded by `sift config privacy acknowledge-upload`. The command prints the provider, the fact that source content may be processed by that provider, and how to disable upload. Non-interactive use requires an explicit equivalent flag. `--no-upload` always overrides configuration.

Dynamic execution requires all of the following:

- supported operating system;
- `--enable-execution` or equivalent explicit configuration;
- Docker or Podman capability check;
- image and resource policy validation.

If any condition is missing, Sift generates tests without executing them and emits a non-finding diagnostic.

## Secure target resolution

The resolver establishes one canonical repository root. Every candidate path is canonicalized and verified to remain inside that root after symlink evaluation. Git diff uses NUL-delimited output. Paths are transported as slices, not comma-separated strings. Ignore patterns, maximum file size, maximum file count, and supported extensions are applied once by the resolver so analyzers see the same input set.

Invalid or escaping paths fail closed. Unreadable individual files produce typed diagnostics without silently expanding scan scope.

## Generated-code execution

The existing direct host process runner is removed. Linux and macOS use Docker or Podman with:

- network disabled by default;
- read-only root filesystem;
- non-root user;
- bounded CPU, memory, process count, time, and output;
- a fresh temporary workspace containing only the generated test and explicitly required source files;
- no API keys, Git credentials, host environment, or writable repository mount.

Windows is generation-only. If no approved backend is available on Linux/macOS, Sift is also generation-only.

## Error model

Errors are typed as configuration, policy, target, analyzer, integration, or internal failures. Expected environmental conditions such as an unavailable registry, missing container backend, or analyzer timeout are diagnostics rather than fabricated security findings. Fatal policy and target errors stop the scan. Individual analyzer failures are reported and produce a non-zero partial-scan exit code while preserving successful results.

Exit codes are documented and tested:

- `0`: scan completed and policy did not fail;
- `1`: policy threshold reached by findings;
- `2`: invalid configuration or target;
- `3`: partial scan caused by analyzer/integration failure;
- `4`: internal failure.

## Accuracy model

Stage B introduces evidence-first normalization. Findings with the same fingerprint are merged while preserving all analyzer evidence. A deterministic analyzer may establish a blocking high-confidence result. An LLM-only result defaults to non-blocking until it includes valid location/evidence and satisfies configured confidence policy. Temporary registry failures never become malicious-package findings.

Suppression supports a project baseline and explicit rule/path entries. Suppressed findings remain visible in audit output with their reason. New findings relative to the baseline can be used for pull-request gating.

## Testing strategy

- Table-driven unit tests for pure logic.
- Temporary repositories for target, Git diff, symlink, and path-containment tests.
- Golden tests for terminal-normalized JSON and SARIF output.
- Contract tests for analyzer and integration interfaces.
- Fake HTTP servers for registries and LLM transport; CI never requires an API key.
- Positive and negative fixtures for every Semgrep rule.
- Container integration tests run only when the backend is available and are separately labeled.
- Fuzz tests target path parsing, unified diff parsing, LLM structured-output parsing, and finding normalization.
- Race tests run on Linux; build tests cover Linux, macOS, and Windows.
- Benchmarks cover full scan, diff scan, cache hit, and cache invalidation.

## Pull-request sequence

### Stage A — security and testing foundation

1. Test and CI foundation.
2. V2 core interfaces and Finding schema.
3. Secure target resolver.
4. Privacy, API-key handling, and upload consent.
5. External command runner and isolated generated-code execution.
6. Release and open-source security gates; publish `v0.2.0-alpha.1`.

### Stage B — accuracy-first scanner improvements

7. Evidence-first normalization, deduplication, suppression, and baseline.
8. Semgrep rule tests and dependency-verifier accuracy.
9. Privacy-safe LLM analyzer and evaluation harness.
10. Diff/cache correctness, performance, migration documentation, and `v0.2.0` release.

## Pull-request governance

Every pull request includes scope, out-of-scope items, tests run, security impact, compatibility impact, and rollback instructions. It starts as draft and becomes ready only after CI passes. Work on the next dependent pull request begins only after the maintainer has reviewed the current one. The agent never merges without explicit authorization.

If GitHub attributes the pull request to the maintainer's own account and therefore prevents a formal self-review request, the maintainer reviews the diff, leaves comments if needed, and merges manually.

## Stage A completion criteria

- CI enforces formatting, vetting, unit tests, race tests, and supported-platform builds.
- High-risk modules have deterministic automated tests.
- Source upload and generated-code execution are both opt-in and fail closed.
- Direct host execution of generated code is gone.
- Paths and external commands pass adversarial tests.
- JSON and SARIF v2 contracts are stable and documented.

## Stage B completion criteria

- Every shipped Semgrep rule has positive and negative fixtures.
- Registry transport failures cannot create package-security findings.
- Findings provide evidence, confidence, provenance, and stable deduplication.
- LLM evaluations report precision, recall, and false-positive rate.
- Cache invalidation includes content, policy, rule, and analyzer versions.
- `v0.2.0` documentation and migration instructions cover all breaking changes.
